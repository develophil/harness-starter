# 릴리즈 노트 작성

## 입력 계약

- 버전과 게시일을 받습니다.
- 변경 항목은 `id`, `type`, `scope`, `summary`, `userImpact`를 가지며 호환성 파괴 변경은 `migration`을 포함합니다.
- `type`은 `breaking`, `feature`, `fix`, `docs` 중 하나입니다.

## 절차

1. 필수 필드와 타입을 확인하고 누락 항목은 임의로 채우지 말고 알립니다.
2. 중복 항목은 합치고 내부 전용 항목은 사용자 변경과 분리합니다.
3. `호환성 변경 → 새 기능 → 수정 → 문서 → 중복·내부 전용` 순서로 묶습니다.
4. 각 항목은 내부 식별자보다 사용자 영향을 먼저 씁니다.
5. 호환성 변경은 이전 방법, 새 방법, 전환 절차를 함께 씁니다.

## 출력 계약

- 제목에 버전과 게시일을 씁니다.
- 첫 문단은 사용자가 체감할 핵심 변화만 요약합니다.
- 각 유형은 빈 절을 만들지 않으며 해당 항목이 없으면 생략합니다.
- 사실을 추측하지 않고 입력에 없는 위험이나 효과를 덧붙이지 않습니다.

## 자체 검증

- 모든 입력 항목이 한 번만 반영되었는가?
- 호환성 변경마다 이전·새 방법·전환 절차가 있는가?
- 사용자 영향이 내부 식별자보다 먼저 보이는가?
- 버전, 게시일, 요약, 유형별 목록이 있는가?
